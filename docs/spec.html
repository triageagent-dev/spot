Specification · spot repository

Spot

The spot is an always-on teammate for one workspace of the Triage core. A supervisor wakes a Go agent loop in turns; the loop asks a model and runs MCP tools of the core, ego and connectors. It has no shell, no filesystem tools and no cluster RBAC, and the core has no Kubernetes client.

01

The loop

A wake is why the supervisor starts a turn. Every wake is an empty conversation: nothing is resumed, so a model call never pays again for earlier tool output. Continuity is what the spot reads at the start of a wake and the core’s memory (upsert_memory_item, search_memory). A pod with an empty /state loses only the day’s token count and the room cursors. A workspace is one tenant of the core (ADR-095 lives there, ADR-098 in docs/adr); ego scores agents from their telemetry; a connector is an MCP server holding its own credentials.

TermMeaning
wakeReason: startup, tick (the agent scheduled it), edge (the core changed) or human (someone wrote). The wake prompt is the first user message: reason, facts, token budget left.
turnOne run of the agent loop: core tools first, then connector reads; verify before any write; record on the issue.

How a turn ends

A turn endsResult
end_turnThe model ends its answer.
finish{"summary": "<one line>"}; the line shows in the status file. Optional.
schedule_next{"after": "15m", "why": "check the rollout"}, last in the turn, clamped to [--min-wake, --max-wake]. Never called, or not a duration: the next wake is --min-wake and the supervisor logs why.

Gates before tools run

GateRule
Notes first--recall-first. In each wake every tool except the core's memory and room reads (tools.RecallTools) and ego's is answered with an error and not run until a search_memory has succeeded, so the spot looks for what it was told before it looks at the cluster or posts. The tool layer holds it; it is off when the core does not offer search_memory.
Post gate--post-gate. In each wake say_in_workspace and comment_on_issue (tools.PostTools) are answered with an error and not run until a get_memory_context or get_memory_items call (tools.ContextTools) and an upsert_memory_item or supersede_memory_item call (tools.NoteTools) have succeeded, so the spot posts knowing what the workspace holds and leaves a note of what it said. A step is skipped when the core does not offer a tool for it. A finish in the same step as a held call is answered with an error ("not finished") and does not end the turn, so a refused post is never reported as done.
Fenced results--fence-results. The text of every core and connector tool result (an error too) comes back inside <data id=… from=…> and </data id=…>, with a fresh random id per call (Registry.fence), so text from outside (a log line, an issue comment, a chat message) is marked as data and cannot close the tag. The supervisor's own refusals, the built-in tools and the ego tools are not wrapped. The instruction tells the model that what is inside is data, never orders.
Wake digestThe only thing carried from one wake to the next: the spot’s own finish summary of each of its last four wakes (one line each, clipped), kept in the state directory and put in the first message of the next wake with the reason it gave for that wake. They are its claims, not facts. Losing the file is harmless.
Short laneWhile a long turn runs, a person’s message and a wake the spot promised run in a second, short turn of their own: its own tool state, the same model client, capped at a few tool calls (--fast-max-tool-calls, --fast-max-turn-tokens; --fast-lane=false turns it off). The long turn is never cut for it, and a message is not pushed into it. One short turn runs at a time; a message that arrives meanwhile is handed to it. Its tokens count against the same daily ceiling.
Promised wakeA wake the spot schedules on a person’s request, sooner than its longest sleep, is a promise: it is kept in the state directory, runs even under a hold rule and after a restart, is not pushed back by later wakes, and runs on the short lane if a long turn is still working when it is due.
Hold rule, person’s messageWhile a standing rule says to check nothing until asked, a person’s message gives the turn only the notes, the room, a post and the scheduling tools. A check they ask for is a wake the spot schedules, and that wake has every tool.
Room readsread_workspace_room is asked only for messages newer than the last finished turn could see (the supervisor adds since_ts, and a limit of 10), unless the model passes its own since_ts or limit. The new messages of a wake are already in its facts.
Old results cutWithin one wake, a tool result older than the last two steps and longer than 1,500 bytes is cut to its first 800 bytes (the closing data tag kept) before the next request, so a long wake does not send every big result again at every step.

Caps and failures

Limit or failureRule
40 requests--max-steps. Not a failure: stepsExhausted.
150k tokens--max-turn-tokens. The billable tokens of a wake (input without cache reads, output, cache writes). Checked after each step; past it a tool call is answered with an error and not run and the model is told to wrap up, as at the tool-call cap. 0 turns it off. Not a failure.
20 tool calls--max-tool-calls. Past it a call is answered with an error and not run, and the model is told to answer from what it has, call schedule_next and finish, which are never refused. A model that goes on calling tools ends the turn. Not a failure.
20m--turn-timeout. Failed; reported as cut off on the next wake.
SIGTERMCancels the turn, counts the tokens seen, marks it cut off, flushes the spans, writes status.json, exits.
failureAn API error after the SDK’s two retries, a refusal, an answer cut at the output cap twice, a timeout, no core tools. The next wake backs off from --min-wake, doubling to --max-wake; edges wait too. A 401 or 403 sets authFailed. A failing tool is not a failed turn.

Between turns

No model is used. With --core-api-url the core pushes content-free frames over a websocket (/v2/messenger/spot/ws); the supervisor reads the core after a 1.5 s pause, so a burst is read once. While the stream is down, or without the flag, it polls every --poll-interval; status.json triggers says stream or poll.

EdgeRule
issue changeNew issue, reopen, severity change or new comment (list_open_issues). Wakes after --edge-cooldown. Changes during a turn are held; comment counts are re-baselined, since the agent comments itself.
message naming the spot@<name> or the name. Wakes 5 s after the last turn.
person’s other messageWaits up to --chat-batch (10m).
machine messageNever wakes alone; a fact in the next prompt. Hop count 2 or more is dropped.
held edgesAt most 20; machine messages go first, then the oldest. Past the hourly cap, or inside the backoff, edges wait for the scheduled wake.
room cursorsSaved in /state/supervisor; a message sent while the pod was down is news on start. A room’s first read only sets the cursor.
failed wakeFailed before its first model request (no core tools, rejected credential, timeout): its facts are put back. An edge put back three times is dropped.
heartbeatupsert_memory_item, kind note, stale_after twice the next sleep (at least 5m), refreshed after every successful turn. A failed turn leaves it, so reflection resumes.
core downNo core connection or tool list fails the turn (coreDown); the model never starts without its tools.

A message while a turn runs

With the stream up, a person’s message is handed to the running turn: the model sees it with the next tool results, or before the turn would end. Other messages, and one the model never saw, wait for the next wake.

Engines

The schedule and the turns run in one of two engines, chosen with --engine.

EngineWhat it is
local (default)The supervisor in this process owns the timers, the promised wake, the hold rule and the two lanes, and runs the loop. A restart resumes at the next wake; a turn it cuts is reported on the next start.
temporalA Temporal workflow per spot owns them, and a child workflow runs each turn. The pod stays the only place that calls the model and the tools; the service holds the schedule and the history. Temporal Cloud or a service of your own: the settings are the same.
With --engine=temporalRule
Spot workflowOne long-running workflow per spot (spot-<name>). The scheduled wake and the wake a person asked for are durable timers: one that comes due while no pod runs is run by the next. The hold rule, the schedule, the failure backoff and the early-wake handling are the same as in local (the supervisor’s schedule.AfterTurn, shared). A startup wake is skipped when the schedule survived the restart. The history is carried over (continue as new) when the service suggests it.
LanesA person’s message runs in the short lane, everything else in the long lane, one wake at a time in each, side by side. What arrives while a lane is busy waits and is one wake when it frees. A wake that is due while the long lane works runs in the short lane. The short lane has the caps of --fast-max-tool-calls and --fast-max-turn-tokens.
Tasksstart_task {"title", "goal"} (up to 3 per turn; not offered under a hold rule or with --max-tasks 0) starts a task when the turn that asked ends: a child workflow of its own, in the task lane, with a new conversation that holds only the goal, the standing notes and the digest, the usual caps, the same tools and no schedule_next or start_task. Up to --max-tasks (3) run at once beside the long and the short lane, each with its own tool connections and gates; up to 10 more wait for a place and a task past that is dropped. A task changes no schedule and no promise. When it ends, its one-line result is a digest entry (task <title>) that the next wake reads, and the core gets a line of activity for it. A task posts to the room itself when its goal says so. Under a hold rule a task does not run. An operator can list, stop, kill, restart and drop tasks through the core (the control frame).
TurnA child workflow runs the same loop as local (agent.RunLoop); each model request and each tool call is an activity that heartbeats, so a pod that dies is noticed in seconds and the next one resumes the turn at its step. The conversation is the workflow’s history. The instruction and the tool list are not in it: they are the pod’s.
At most onceA call that may have an effect (every write, every connector tool) is run once. If its pod dies in the middle, the model is told that the call did not finish and may or may not have run, and decides. A read of the core or of ego is run again, up to three times.
PayloadsWith --temporal-payload-key-file every payload, a failure’s message included, is encrypted with AES-256-GCM in the pod before it leaves it: the service holds ciphertext, plus names, timings and sizes. Over TLS or with an API key the spot does not start without the key unless --temporal-plain-payloads says the clear text may go. The key is a file; a payload written with another key is refused.
Payloads kept in the podWith --temporal-local-payloads the history holds only a reference to each payload (its sha-256), and the payload is a file in the state directory: no content, not even as ciphertext, reaches the service. A workflow replays from its history by reading those files, so the state directory must survive restarts; a payload that is gone fails the replay and the operator ends that workflow. A payload nobody read for 21 days is swept, and a run of the spot’s workflow ends after 7 days when nothing is open, so a run never outlives its payloads.
What stays in the podThe intake (trigger stream, polls, held edges, cooldowns, caps), the standing notes, the prompt, the books (usage ledger, digest, heartbeat, stats, status file), the model client, the tools and the spans. The service never calls the model or a tool and holds no credential of them.
FailuresA refused key and a request the model API calls wrong are not retried; other model errors are, up to three times. A turn that fails, or runs past --turn-timeout, is a failed wake with the same backoff as in local. A tool server that is down is left out of the turn, as in local.
CostEach model request, each tool call, the head of a wake (Prepare), its books and the typing indicator are one Temporal action each, and a wake that holds under a rule costs two. Hold, caps and the daily ceiling bound them as before.

The model

All model traffic goes through internal/llm; this section is the Anthropic provider. The request is built for a prefix cache: sorted tools, then the system prompt with a one-hour cache_control breakpoint on its last block, and a short breakpoint on the latest message.

Credentials

--llm-auth picks the model auth mode; federation is Anthropic only. Federation ids are not secrets, but they are flags.

CredentialHow it flows
Key (key, default)A Secret file (--anthropic-key-file or --gemini-key-file for Gemini), re-read on every request. The SDK is built without its environment defaults, so a stray ANTHROPIC_* variable cannot replace the key.
Federation (federation)No Anthropic secret. A projected token (audience https://api.anthropic.com, at /var/run/secrets/anthropic.com/token) is exchanged by the SDK for a short-lived one. The SDK reads federation from the environment, so the process sets ANTHROPIC_FEDERATION_RULE_ID, ANTHROPIC_ORGANIZATION_ID, ANTHROPIC_SERVICE_ACCOUNT_ID, ANTHROPIC_IDENTITY_TOKEN_FILE and, if set, ANTHROPIC_WORKSPACE_ID from its flags: ids and a path, never a credential. ANTHROPIC_API_KEY, ANTHROPIC_AUTH_TOKEN, ANTHROPIC_IDENTITY_TOKEN and ANTHROPIC_PROFILE are unset, since each outranks federation. --anthropic-key-file is refused.
Vertex AI (vertex)Application Default Credentials: the pod’s Workload Identity. Annotate the ServiceAccount (serviceAccount.annotations, iam.gke.io/gcp-service-account) with a Google service account allowed on Vertex AI in --vertex-project. The model id has no prefix.
core tokenA file read on every request: the pod’s projected token, audience triage-core (core.identity: serviceAccount), or a Secret (secret).
pod tokenThe default ServiceAccount token is not mounted (automountServiceAccountToken: false).

The identity token must be fresh at every exchange

The projected token carries a jti claim, and Anthropic rejects one it has seen (jti_reused in the Console’s authentication history). The kubelet rewrites the file at about 80% of tokenExpirationSeconds (600 s, the minimum) and the SDK reads it on every exchange, so a second exchange in the same token’s life can send a used token. Whether the SDK’s cached access token lasts long enough is not tested against the real API, and not worked around.

SignalContent
log and status.json lastErrorOn an authentication-looking failure in federation mode: “Anthropic authentication failed in federation mode; check the authentication history in the Claude Console (jti_reused / match_*)”.
the 401Authentication failed gives no reason; only the Console history does: jti_reused, match_subject_prefix and the other match_* rules, workspace_id_required.
09

Boundary

The spot holds no cluster RBAC; a cluster is reached through a connector, whose own identity is the boundary. The model has no web tool, no subagents, no shell and no file tool, because none exists in internal/tools. The model cannot read a mounted token. The supervisor’s counters are held in memory.

What the spot cannot do

QuestionAnswer
Can it run a shell command or a program?No. There is no shell and no tool that runs a command (internal/tools has none).
Can it read or write a file?No. There is no file tool, and the model cannot read a mounted token.
Can it fetch a URL or search the web?No. There is no web tool.
Can it start subagents?No.
Can it touch the cluster directly?No. The spot holds no cluster RBAC. A cluster is reached only through a connector, by the exact tool names the connector offers, and the connector’s own identity is the limit.
Can it call any core tool?Only the tools the install offers. By default the allowed list is tools.CoreTools; the destructive ones (tools.CoreToolsDenied, for example resolve_issue) are refused by name, even when also allowed. A call to any other name is answered with an error and never sent.
Can it change its own limits?No. The counters live in the supervisor’s memory and the model has no tool to write them.
Can the prompt widen any of this?No. The prompt is best effort; the tool lists and the connector hold.

Identity towards the core

core.identityBehaviour
serviceAccount (default)The spot’s own ServiceAccount: a projected token, audience triage-core, no core Secret, validated by TokenReview. The chart renders a Role and RoleBinding <spot name>-core, labelled triageagent.dev/managed: "true", granting core.verbs (default get, list, create, update) on the one tenant; core.rbac.create: false if the grant is made elsewhere. The core accepts only ServiceAccounts from its own namespace, so the chart is installed there.
secretA bearer token from the Secret core.tokenSecret, usable from any namespace.
certificateThe spot joins the core the way an agent does (the core’s ADR-105): an Ed25519 key of its own in /state/identity, a certificate request over the core’s join websocket, a person approving its fingerprint in the core (the spot logs join pending: spot=… fingerprint=SHA256:…), a certificate that the spot renews itself, and a short-lived access token that the core sends over the stream and the spot writes to /state/identity/token. No core Secret, no projected token, no Role. Needs core.apiUrl and core.caFingerprint (the core’s CA, checked before anything is sent). The first join carries the one-time enrollment key the core minted for the spot (core.enrollKeySecret, a Secret mounted as a file); a spent key left in place is harmless. The spot’s name is its identity: keep spot.name stable. Losing /state means the core must approve the spot again.

Spend

ControlRule
--daily-token-ceilingInput plus output plus cache-write tokens per UTC day (cache reads not counted), held in memory and written through to usage.json, read once at start. At the ceiling no wake starts, edges are held, the loop sleeps to UTC midnight. A turn in flight can overshoot by one turn (bounded by --max-steps, --turn-timeout).
contextEvery wake starts empty; status.json shows each turn’s contextTokens.
the core’s capPolicy budgets.spotTenantDailyTokens over budgets.spotDailyDefaultTokens: new input plus output per workspace per UTC day. After every turn a turn frame goes up the trigger stream (model, input incl. cache reads and writes, cached, output, duration, failed); the core books it as usage kind spot (TUI usage panel) and answers with the budget: the workspace’s spent and cap, and own, what this spot spent as the core counted its turns, which the spot takes as the floor of its own daily counter (so a lost state directory does not give the day back). Over the cap it refuses say_in_workspace and set_workspace_status, and the supervisor pauses all wakes until the budget lifts or UTC midnight. Frames sent while the stream is down wait (the last 100 are kept).
stats frameState, turns and wakes by reason today, failures in a row, context size, own token counts and ceiling, why it is paused (its own ceiling or the workspace cap), its limits and choices (model, step, tool-call and token caps, wake timing, core-tools mode, gates, connector names with their tool names; never a URL, path or credential), next wake. After each turn, on a trigger-mode change and every two minutes, for the TUI’s workspace panel. Counts and labels only.
wake frameOne line of activity when a wake ends, for the TUI’s timeline: when, the reason (startup, tick, edge, human, promise), the lane (long or short), the outcome (turn, failed, or a wake with no model call: quiet, hold, ceiling), duration, steps, tool calls, paid tokens, cache reads and output, and when the spot wakes next and why. Counts and labels only, never what was said. Dropped while the stream is down: a gap in the timeline is true, a replay of old wakes is not.
control frame (core to spot){"control":{"id","op","task"}}: an operator (a person through the core, never a spot) acts on one wake the spot has in hand. op is list, stop (cancel: the turn ends at its next step and closes its tools; not a failure), kill (terminate: cut at once), restart (a task: stop, then start the same task again) or drop (a task that waits for a place). task is a key a list gave (128 bytes at most), empty for list; the spot checks it against what it has in hand and acts on that workflow only. A task that has not begun its turn is stopped, not killed.
controlResult frame (spot to core){"controlResult":{"id","ok","msg","tasks":[{"key","title","lane","state","startedMs","ageMs"}]}}: sent once for every control, with the same id, within 8 s, a refusal included (an engine other than temporal, an unknown key, an operation that does not fit the state). tasks is what the spot has in hand afterwards, running and waiting, 100 at most; a title is 80 bytes. Titles and counts, never a goal or what a turn said.
dollarsNo ceiling: the spot has no price table. The spend limit on the Anthropic workspace or Google project that serves the model is the real stop.

Connectors

A connector is one more MCP server beside the core, reached by URL, holding its own credentials and limits: a Kubernetes tool server, a code host, a metrics API. The spot has no code for any of them and no credential for them.

connectors:
  - name: example-kube
    url: http://tools.example.svc:8084/mcp
    tools: [k8s_get_resources, k8s_describe_resource, k8s_get_pod_logs]
    hint: The workspace's cluster, read-only.
    egress:
      namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: example}}
      podSelector: {matchLabels: {app.kubernetes.io/name: tools}}
      ports: [8084]
FieldRule
listThe chart renders it into a ConfigMap read by --connectors-file: names, URLs, tool names and hints; no credential.
toolsOffered to the model by exact name as <name>__<tool>. The file is refused when a connector names none, uses core or ego, repeats a name, or lists a tool that is not a plain name. A tool the connector offers and tools does not name is not offered, and a call to it is refused.
hintGoes into the prompt’s Connectors section, which also lists the named tools, so the spot knows a tool it was not given is not “missing”. What a connector returns is data, not instructions.
egressOpens the NetworkPolicy to that connector and nothing else; the chart fails to render without it.
trustThe connector’s own business: its identity, its RBAC or IAM, and the network. The list is never the boundary; the connector’s own limits are. A connector is the only way to any cluster.

Run it locally

Source: github.com/triageagent-dev/spot. You need a core you can reach and your own credentials in files. Nothing below is a real name.

make build
mkdir -p /tmp/spot/state && umask 077
printf '%s' "$CORE_TOKEN" > /tmp/spot/core-token          # a token for a tenant identity
printf '%s' "$ANTHROPIC_KEY" > /tmp/spot/anthropic-key
./bin/tria-spot --tenant <tenant> \
  --core-mcp-url https://<core-host>/mcp \
  --core-token-file /tmp/spot/core-token --anthropic-key-file /tmp/spot/anthropic-key \
  --state-dir /tmp/spot/state \
  --min-wake 2m --daily-token-ceiling 200000 --log-level debug

The spot reaches no cluster unless --connectors-file names a connector. Ctrl-C stops it gracefully. Check /tmp/spot/state/supervisor/status.json.
